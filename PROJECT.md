# Machine Learning Studio — Project Reference

A document to prepare from before an interview. It explains what the project is, what it
is built with, how it is put together, and — most importantly — **why** each decision was
made. Interviewers rarely care that you used X; they care that you can explain why X and
not Y.

---

## 1. The one-paragraph pitch

> "Machine Learning Studio is an interactive learning site covering 42 machine learning
> concepts. Every concept page has three things side by side: a visualisation you can
> manipulate, the mathematical formula with the reader's own current numbers substituted
> into it, and a step-by-step trail of the algorithm's logic. Nothing is a static
> illustration — you can retype any value, drag points on a chart, edit a weight matrix,
> or add a layer to a neural network, and every number, formula and picture recomputes
> live. It is a zero-dependency static site: no framework, no build step, no server."

**If you only remember one thing:** the central design goal was *"the learner edits the
input, and the mathematics visibly follows."* Every architectural decision serves that.

## 2. Tech stack

### What is actually used

| Layer | Choice | Why |
|---|---|---|
| Markup | Plain HTML5 | 7 hand-written files; everything else is generated at runtime |
| Styling | Plain CSS (~2,500 lines) | Custom properties for theming; no preprocessor needed |
| Logic | Vanilla JavaScript (ES2020+) | No framework — reasoning below |
| Maths rendering | **KaTeX 0.16.9** via CDN | The only third-party runtime dependency |
| Graphics | **Inline SVG**, generated by hand | Plus one `<canvas>` for pixel-level image work |
| Storage | **localStorage** | Theme choice and sidebar state |
| Dev server | **Python standard library** (`serve.py`) | Nothing to install |
| Hosting | **GitHub Pages** | Static files, so hosting is free and trivial |
| Version control | Git | 29 commits |

### What is deliberately NOT used

No React, Vue, Svelte. No webpack, Vite, Rollup, or any bundler. No TypeScript. No npm
packages at runtime. No CSS framework (no Tailwind, no Bootstrap). No backend, no
database, no API.

### The interview question you will get: "Why no framework?"

Have a real answer ready. This one is defensible:

1. **The output is a static educational site.** There is no user state to synchronise
   across a large component tree, no routing beyond a query parameter, no data fetching.
   The problems a framework solves were not present.
2. **Longevity.** Educational content should still run in five years. A build-free site
   made of HTML, CSS and JS has no dependency tree to rot, no `npm install` that breaks,
   no framework major version to migrate.
3. **Deployment is `git push`.** GitHub Pages serves the files as they are. No CI step,
   no build cache, no node version pinning.
4. **Page weight.** Loading React + ReactDOM to draw an SVG scatter plot is a poor trade
   when the plot is 40 lines of `createElementNS`.

**The honest counter-argument** (say this too — it shows judgement): a framework would
have helped with the repetitive UI state inside the 24 interactive labs. Each lab manages
its own state manually and calls its own `render()`. React's reconciliation would have
removed that boilerplate. The trade was accepted because the labs are independent and
never share state with each other.

## 3. What the project contains

- **42 concept pages** across **5 categories**:
  Foundations (12), Classification (9), Graphical Models (9), Clustering (9),
  Neural Networks (3)
- **24 distinct interactive "engines"** — the code that powers a lab
- **~15,500 lines** of hand-written HTML, CSS and JS

### Algorithms actually implemented from scratch

No ML library was used. Every algorithm is implemented directly in JavaScript:

| Area | Implemented |
|---|---|
| Classification | k-NN, decision trees (Gini + MSE splits), LDA, logistic regression, perceptron, SVM / hinge loss, RBF kernels |
| Clustering | k-means, k-medoids, agglomerative + divisive hierarchical (single/complete/average linkage, with dendrogram), DBSCAN, spectral clustering |
| Graphical models | Bayesian networks, d-separation, Markov random fields, belief propagation, Markov chains, HMMs (forward, Viterbi, Baum–Welch) |
| Statistics | MLE, MAP, Bayesian posterior updates, bias–variance simulation, kernel density estimation |
| Neural networks | Full forward/backward propagation, 6 activations, 3 loss functions, gradient descent with momentum |
| Linear algebra | Jacobi eigenvalue decomposition, 2×2 and 3×3 matrix inversion, affine transformations |

**Talking point:** implementing k-means or backpropagation yourself is a legitimate thing
to discuss in an ML interview. You can explain the assign/update loop, or why softmax +
cross-entropy collapses to `a − y`, because you wrote it.

## 4. Architecture

### 4.1 The core idea: one shell, many pages

The naive approach is 42 HTML files. That means 42 places to update when the header
changes. Instead:

```
pages/algorithm.html?id=k-means
pages/algorithm.html?id=backpropagation
```

**One** HTML file (`pages/algorithm.html`, 67 lines) serves all 42 concepts. It contains
an empty `<div id="algorithm-page-root">`. JavaScript reads the `id` query parameter,
looks the concept up in a catalog, and builds the page.

This is the **data-driven page** pattern. Adding a concept means adding a data entry, not
creating a file.

### 4.2 Layered file structure

```
DATA LAYER
  assets/algorithms.js      The catalog. 42 concept definitions: id, title,
                            category, which engine to use, prose for the
                            deep-dive section. Pure data, no DOM code.

ENGINE LAYER
  assets/nn-engine.js       Neural network maths. No DOM code at all —
                            it computes, the page renders.

UTILITY LAYER
  assets/common.js          41 shared utilities: chart scales, SVG helpers,
                            the data-table editor, the matrix editor, drag
                            handling, KaTeX wrapper, statistics helpers.

RENDER LAYER
  assets/algorithm-page.js  The 24 interactive labs (largest file, 8,571 lines)
  assets/catalog.js         Home and category page listings
  assets/site-nav.js        Sidebar, search, prev/next, footer, theme
  assets/home-hero.js       The live demo on the landing page
  assets/home-sections.js   Featured questions + full index

PRESENTATION
  assets/styles.css         The entire design system
```

**Dependency direction is strictly one-way:** presentation depends on render, render
depends on utilities and data, data depends on nothing. `nn-engine.js` and
`algorithms.js` have zero DOM references, which is why they can be unit-tested in Node
without a browser.

### 4.3 The engine registry pattern

Each concept declares which engine renders it:

```js
{ id: "k-means", engine: "partition", options: { focus: "kmeans" } }
```

At the bottom of `algorithm-page.js` there is a lookup table:

```js
const engines = {
  knn: mountKnn,
  tree: mountTree,
  partition: mountPartition,
  backprop: mountBackprop,
  // ...24 total
};
engines[definition.engine](workspace);
```

**Why this matters:** engines are reused. `partition` powers three pages (k-means,
k-medoids, partition-based clustering) — the page's `options` tell it which mode to lock
into. 42 pages need only 24 engines.

### 4.4 The anatomy of one lab

Every `mount*` function follows the same shape. Know this pattern — it is the heart of
the project:

```js
function mountKnn(rootNode) {
  // 1. Write the markup (controls on the left, output on the right)
  mountSection(rootNode, title, intro, `...html...`);

  // 2. Grab references to the controls
  const kInput = rootNode.querySelector("#knn-k");

  // 3. Hold the editable state
  let points = knnDefaults.map(p => ({ ...p }));

  // 4. Attach an editor that mutates that state
  const editor = U.dataEditor(node, {
    columns: [...],
    rows: points,
    onChange: rows => { points = rows; render(); }   // ← re-render on edit
  });

  // 5. ONE render function recomputes everything from current state
  function render() {
    const result = /* run the algorithm on `points` */;
    U.renderMetrics(output, [...]);        // result tiles
    renderFormulaCards(mathNode, [...]);   // formula + substituted numbers
    U.renderSteps(stepsNode, [...]);       // the logic trail
    const chart = U.makeChart(plot, {...}); // redraw the SVG
  }

  // 6. Every control calls render()
  kInput.addEventListener("input", render);
  U.onRedraw(render);   // also re-render when the theme changes
  render();
}
```

**The key architectural rule: there is exactly one `render()` per lab, and it rebuilds
everything from current state.** No partial updates, no diffing, no "update just this
bit". This is essentially manual React — state changes, render runs, output is a pure
function of state. It makes the labs simple to reason about and impossible to get into an
inconsistent state.

### 4.5 Shared UI components

Rather than repeat editing UI in 24 labs, three reusable pieces live in `common.js`:

**`dataEditor(container, config)`** — an editable table. Add/delete rows, load preset
datasets, per-cell change events. This is what makes "edit the input data" work
everywhere. Includes `setCell()`, a fast path that updates one cell without rebuilding the
table — used during dragging so the numbers track the cursor smoothly.

**`matrixEditor(container, config)`** — an editable matrix, with optional row-stochastic
normalisation (each row is forced to sum to 1). Used for HMM transition/emission matrices
and neural network weight matrices.

**`draggable(node, svg, chart, onDrag)`** — makes an SVG element draggable in *data*
space, not pixel space. It uses the SVG's screen CTM (coordinate transformation matrix)
and the chart's inverse scales to convert a mouse position back into data coordinates.

## 5. Notable technical problems and how they were solved

These are the strongest interview material. Each is a real problem with a real solution.

### 5.1 Theme-aware SVG charts

**Problem.** Adding dark mode is easy for HTML — CSS custom properties change and
everything restyles. But SVG charts are drawn from JavaScript with
`setAttribute("fill", "#1f7a70")`. Presentation attributes cannot read CSS variables, so
~120 hardcoded colours across the labs would have stayed light-themed on a dark page.

**Solution, in three parts:**

1. Define a semantic chart palette as CSS variables (`--c-a`, `--c-b`, `--c-grid`, …)
   with a light and a dark value.
2. `MLUtils.chartColors()` reads them once via `getComputedStyle` and caches the result
   per theme.
3. Charts bake colours into attributes, so CSS alone cannot repaint them. Each lab
   registers its `render` with `MLUtils.onRedraw()`; toggling the theme fires an event
   that invalidates the cache and re-runs every registered render — repainting the plots
   **while preserving whatever data the reader typed**.

### 5.2 Backpropagation computed live, not hardcoded

**Problem.** The original neural network page had every number hardcoded — a fixed
worked example. Change an input and nothing happened.

**Solution.** A standalone React/Vite prototype existed with a well-built TypeScript
engine. It was ported to dependency-free JavaScript (`nn-engine.js`, 361 lines) so the
site keeps a single toolchain. It supports arbitrary architecture (any depth, any layer
width), a bias per neuron, per-layer activations, and three loss functions.

**The detail worth mentioning in an ML interview:** two activation/loss pairings collapse
mathematically. Softmax with categorical cross-entropy, and sigmoid with binary
cross-entropy, both give `δ = a − y` — the activation derivative and the loss derivative
cancel exactly. Computing them separately is not just slower, it is numerically unstable
near `a = 0` or `a = 1`. The engine detects the pairing and takes the shortcut, and the
page *explains* that it did.

**How it was verified:** the port was checked against the standard hand-worked 2-3-3-2
example before any UI was attached. Activations, loss and both delta layers matched to
four decimal places. Softmax outputs sum to 1.0000000000; both shortcut paths are exact
to 1e-12.

### 5.3 Making the vanishing gradient measurable

The page reports the ratio `‖δ_output‖ / ‖δ_input‖`. With sigmoid activations it reads
about **252×**; switch every hidden layer to ReLU and it drops to about **10.7×**. This
turns a textbook claim into a number the reader watches change. Sigmoid's derivative
peaks at 0.25, so each layer shrinks the gradient by at least 4×.

### 5.4 Search without a search library

A `⌘K` command palette searches all 42 concepts. No library — a small ranking function:

- exact title match → rank 0
- title starts with query → rank 1
- title contains query → rank 2
- summary/category contains query → rank 3
- **subsequence match** → rank 4

The subsequence fallback is why typing `knn` finds "Nearest Neighbour": it walks the
query characters looking for each one later in the title.

### 5.5 Layout bug worth knowing

Editor tables overflowed their sidebar panel. The cause was subtle: a browser's default
`<input>` has an intrinsic width of ~150px, which sets the *minimum content width* of a
fixed-layout table, so the table refused to shrink. Fix: `size="3"` on the inputs to
shrink their intrinsic width, with `width: 100%` in CSS to make them fill the column they
are actually given.

A second, related one: a scroll container's vertical scrollbar consumed ~15px of client
width while the table's `width: 100%` still resolved against the wider padding box,
leaving phantom horizontal scroll. Fixed by reserving the gutter with padding.

## 6. Feature list

**Learning features**
- 42 concept pages, each with editable input data
- Live formulas: the general rule, then the same rule with the reader's numbers in it
- Step-by-step logic trail with a "next step" control
- Deep-dive section per page: intuition, core mathematics, when to use, how it fails
- Draggable data points on charts
- Preset datasets chosen to expose failure modes (e.g. "two moons" defeats k-means)
- Dendrogram for hierarchical clustering; live distance matrix showing the next merge

**Site features**
- Live animated demo on the landing page — four algorithms on one dataset, click to add a
  point
- Collapsible sidebar with the full concept tree, current page marked
- `⌘K` / `Ctrl+K` / `/` search palette with keyboard navigation
- Previous/next links so the whole syllabus reads in order
- Dark mode following OS preference, with an explicit override remembered
- Custom 404, `sitemap.xml`, `robots.txt`, Open Graph tags, inline SVG favicon
- Responsive from 375px to wide desktop

**Accessibility** (a strong differentiator — most portfolio projects skip this)
- KaTeX configured for `htmlAndMathml` so screen readers get MathML rather than
  presentational spans. **This was a real bug:** it had been set to `html`, which silently
  broke 303 formulas for assistive technology on a site made of formulas.
- Every generated editor cell has an accessible name ("x for A1"), covering hundreds of
  inputs
- Results announce via `aria-live` regions as the reader edits
- Skip-to-content link, visible focus rings, `prefers-reduced-motion` support

## 7. Engineering practices to mention

**Cache busting.** Every asset URL carries `?v=<timestamp>`. Without it, browsers serve
stale JS from cache after a deploy. This was discovered the hard way — a page kept
showing old behaviour because the `<script>` tag loaded from cache (`transferSize: 0`).

**Verification by automation, not eyeballing.** Changes were verified by scripting the
browser: load all 42 pages in iframes, click every control, and assert on console errors,
KaTeX render counts, unlabelled inputs, layout overflow, and duplicate links. This caught
bugs a visual check would have missed.

**Real bugs found this way:**
- The decision-tree page was **completely broken** — a temporal dead zone error
  (`derivLines` used before its `let` declaration) meant its maths panel, steps table and
  plot never rendered at all.
- `round(60, 0)` returned `"6"` — the trailing-zero strip ran on the whole string instead
  of just the fractional part, so any whole number displayed with 0 decimals was
  corrupted.
- `clusterPalette` was evaluated once at module load, freezing cluster colours to
  whichever theme happened to load first.

**Progressive enhancement.** If the KaTeX CDN fails, `tex()` falls back to a `<code>`
element so formulas stay readable.

**Performance.** `rafThrottle` coalesces pointer-move events into one paint per frame. The
landing page animation pauses via `IntersectionObserver` when scrolled out of view.

## 8. Likely interview questions

**"Walk me through the architecture."**
Data layer (catalog) → engine layer (pure computation) → utility layer (shared UI) →
render layer (24 labs) → presentation (CSS). One-way dependencies. One HTML shell serves
42 pages via a query parameter and an engine registry.

**"Why no framework?"** — See section 2. Give the reason *and* the counter-argument.

**"What was the hardest part?"**
Theme-aware SVG. CSS variables cannot reach SVG presentation attributes set from JS, so it
needed a resolved-palette cache plus a redraw registry that repaints charts without losing
the reader's data.

**"How did you test it?"**
Scripted browser automation across all 42 pages asserting on errors, render counts,
accessibility and layout — plus validating the neural engine against a known hand-worked
example before wiring any UI to it.

**"What would you do differently?"**
`algorithm-page.js` is 8,571 lines. It should be split into one module per engine using ES
modules. It grew organically and was never refactored. Also: there is no automated test
suite — verification was scripted ad hoc rather than committed as tests.

**"How would you scale this?"**
The catalog pattern already scales to hundreds of concepts. The real limits are the single
large render file (split into modules), and that all 42 concepts load the same JS bundle
(code-split per engine, or use dynamic `import()`).

## 9. Known limitations — state these honestly

1. **`algorithm-page.js` is too large** at 8,571 lines. Should be ES modules, one per
   engine.
2. **No automated test suite.** Verification was scripted in the browser console, not
   committed as repeatable tests.
3. **Dead code.** `assets/introduction.js`, `classification.js`, `clustering.js` and
   `graphical-models.js` total 2,986 lines and are referenced by nothing. They are
   leftovers from the pre-refactor architecture, when each category had its own script.
   They should be deleted.
4. **Query-parameter routing** (`?id=x`) is weaker for SEO than real paths
   (`/concepts/k-means/`). Chosen because GitHub Pages has no server-side rewriting.
5. **KaTeX from CDN** is a third-party runtime dependency and a privacy consideration.
   It could be self-hosted.

Being able to list your own project's weaknesses is one of the strongest signals you can
give in an interview. It shows you evaluate your work rather than just defend it.
